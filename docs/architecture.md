# 実装構成と運用条件

## 保管先

- 業務データ・PDF原本・JSON: Notion。Supabaseなし。
- Web UI: React/Vite。API: Express/TypeScript、Node.js 24。
- 本人認証: サーバー側scryptパスワードハッシュ、8時間の署名Cookie、Origin/CSRF検証。
- Notionトークン: サーバー環境変数のみ。利用者がDB IDをAPIへ渡して接続先を変える機能はない。
- PDF: pdf-lib/fontkit/Noto Sans JP。税込/税抜は書類単位、税区分は明細単位。数量・円単価は整数、50明細まで。

## 発行の再開

1. サーバーが下書き版・発行者設定版・税区分を検証。
2. 既存台帳の最大番号とローカルカウンタを照合し、番号を永続予約。
3. 初回の発行者・宛名・税額・取引内容を固定し、Notionへ「発行処理中」として保存。
4. PDFを生成し、処理用ジャーナルに保存してからNotionへ添付。
5. 保存PDFを読み戻してSHA-256を照合。
6. Notionを「発行済み」に更新。応答喪失の場合は再試行時に原本と台帳を照合する。
7. ジャーナルの処理用JSON/PDFをNULLにし、発行ID・番号・照合ハッシュだけ保持。操作履歴をNotionへ同期。

通信エラー時に新しい番号を割り振らない。予約番号は再利用しないため、失敗や中断による欠番は許容する。操作履歴の同期失敗は発行成功と分け、永続outboxから毎分または画面で再試行する。発行自体の再開は本人の確認画面を経由し、勝手にバックグラウンド発行しない。

## ローカルジャーナルについて

`DATA_DIR/operations.sqlite`は業務台帳の複製ではなく、排他・番号予約・中断処理・同期待ち操作履歴・原本照合ハッシュのための領域。ただし中断中は宛名・明細・PDFを含むため、非公開の永続ボリュームへ保管し、バックアップとアクセス制限が必要。

**初版は単一利用者・単一プロセス・単一インスタンス専用。** `instance.lock`で同じディレクトリの二重起動を拒否する。異なるコンテナへ同じアプリを水平分散したり、複数端末で別のDATA_DIRから同じNotion台帳に発行したりしない。サーバーレスの一時ファイル領域へ置かない。

ノートPCで動かす場合はそのPCが起動中の間だけ利用できる。常時利用する場合は永続ボリューム付きNode/Dockerホストを選ぶ。GitHub Pagesだけではサーバー側の認証・秘密情報管理・発行処理を実行できない。

## Notionの扱い

APIバージョンは`2025-09-03`に固定し、data source IDを使う。DBの作成はWorkへ委任されたため、このアプリは既存DBを使用し、勝手に作成・スキーマ変更しない。

JSON添付は下書き段階から`確定データJSON`プロパティに保存する。内容は`schemaVersion`, `issuanceId`, `draft`、確定開始後は`snapshot`。確定後の税率・計算結果・発行者は当時のスナップショットを使う。Notionページ本文の明細表は機械的な保存元ではなく、現在は読み取らない。Workから下書きを更新する機能は次段階で共通APIへ接続する。

再ダウンロード時はNotionのページを再取得して期限付きURLを更新し、保存されたPDFを返す。URL自体を恒久的な保管先として保存しない。

Notion上での直接編集はアプリの制約を迂回できる。発行済みデータの整合性とローカル保存ハッシュを検証するが、Notionの管理者による削除・編集を完全に禁止する仕組みではない。台帳は非公開とし、発行済みはアプリから操作する。電子帳簿保存法の完全適合を宣言しない。

## 初版の範囲外

- 複数利用者のアカウント・Notion OAuth・課金・公開SaaS運用
- Workからの確定発行・下書き操作
- 1書類内の税込/税抜入力の混在、小数数量、ロゴ・印影のPDF配置
- 自動一括バックアップ・復元、メール/LINE送信、会計連携
- 税率マスタの管理画面（初版はレビュー付きソース変更）。食品1%は準備中で確定発行不可
- 税務上の適用判定や登録番号の実在確認の自動化

税率マスタと根拠URL・確認日・適用期間は`shared/tax-policy.ts`で管理。食品8%を予定日だけで自動変更しない。1%を有効化する変更には制度確認・期間境界/終了後の税率・混在テスト・UI案内の再レビューが必要。
